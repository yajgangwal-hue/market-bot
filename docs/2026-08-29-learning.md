# Making it learn from its own trades

## What was already there, and why it never learned anything

`learning.py` does train a model. Its features are `trust_score`,
`age_minutes`, `text_length`, `entity_count`, `platform_bluesky/x/rss` — it is
a model of *social posts*. It shares **no feature** with the gate that decides
trades, so nothing the bot ever did could teach it anything. The training file
also had to be written by hand, and none existed.

`trade_learning.py` closes that loop: the features are the candidate's own
measurements, and the label is what the trade went on to do.

## Two design choices that mattered more than the model

**Learn from every blocker survivor, not only from taken trades.** Learning
from taken trades would mean learning from seven rows, and would be
selection-biased — the model would only see setups the score already liked. A
candidate that cleared every hard blocker but scored 54 has an observable
forward outcome too, and separating 54-that-worked from 54-that-did-not is
exactly the job. This turns 7 usable rows into **781**.

**The model may only ever subtract.** It is a veto on candidates the
hand-built gate already accepted, never a reason to enter something the gate
rejected. A broken or overfitted model therefore costs missed trades rather
than losses, and an `UNPROVEN` model is ignored entirely. Tests enforce both.

## The finding that made it work

The obvious label — *did this trade make money* — is close to unlearnable
here:

| Label | Out-of-sample AUC | Brier | Base-rate Brier |
|-------|------------------|-------|-----------------|
| R > 0 (any profit) | **0.543** | 0.2538 | 0.2856 |
| R ≥ 0.5 | 0.617 | 0.2506 | 0.2895 |
| **R ≥ 1.0 (adopted)** | **0.619** | **0.2426** | 0.2680 |
| R ≥ 2.0 | 0.612 | 0.1817 | 0.1612 (worse) |

AUC 0.543 is a coin flip. Worse, the model trained on `R > 0` ranked the
**biggest winners below average**: its top decile had mean R +0.47 against
+0.94 for the out-of-sample set as a whole.

The reason is structural. This strategy's profit comes from a long right tail
— one +4.5R trade carried the whole two-year record — and a win/loss flag
throws that information away. It teaches the model to prefer frequent small
winners, which is the opposite of what a trailing stop exists to capture.
Asking *"will this become a meaningful winner"* keeps the magnitude in the
label and lifts AUC to 0.619 on the same features and the same split.

Regularization mattered too. Light L2 overfitted badly (out-of-sample Brier
0.33 against a 0.29 base rate). **Every** setting with `l2 = 0.30` beat the
base rate regardless of learning rate or epochs, so the default sits in that
flat region rather than at any single best cell.

## Status gate

A model may veto only if all three hold on the untouched final 30%:

| Criterion | Threshold | Current |
|-----------|-----------|---------|
| Examples | ≥ 150, with ≥ 40 out of sample | 781 / 235 |
| Beats base-rate Brier | by ≥ 2% | 0.2426 vs 0.2680 |
| Discrimination (AUC) | ≥ 0.58 | 0.6192 |

Discrimination rather than calibration is the gate because a veto uses the
model **ordinally** — everything below a threshold is dropped. Calibration is
still reported (currently 0.158, which is poor) so that a badly calibrated
number is never shown to a human as if it were a real probability.

## Honest limits

- **AUC 0.619 is modest.** Real, but nowhere near a reliable predictor.
- **Its effect on actual results is unmeasurable.** At the default threshold
  the veto changes nothing; at 0.35 it removes 1–2 trades and improves the
  result by about $3. On a 7-trade sample that is noise, and choosing 0.35
  because it looked best would be fitting to it.
- **781 examples come from 7 symbols over 2 years.** They overlap heavily in
  time and are not 781 independent observations.
- The model is retrained from history, so it inherits every bias in that
  history — including a period with no serious bear market.

## Usage

```bash
event-aware-trader learn --pine tradingview/learned_filter.pine
```

Regenerates examples, retrains, saves the model, and exports it to Pine. The
`autotrade` loop picks the model up automatically and logs every veto with its
probability. Retrain periodically as real trades accumulate.

## Can the AI part run in TradingView?

**The learning cannot. The trained model can.**

Pine Script has no ML library, cannot call an external API, cannot import a
model file, and runs sandboxed on TradingView's servers. Nothing can be
*fitted* there.

But a logistic model is only a dot product against twelve constants, so
`export_pine()` bakes the fitted weights and their standardisation into
`tradingview/learned_filter.pine`, which evaluates on a chart like any other
Pine function. Training stays in Python; scoring becomes portable.

The split is therefore:

| Step | Where |
|------|-------|
| Generate labeled examples | Python |
| Fit the model | Python |
| Validate out of sample | Python |
| **Score a live bar** | **Python or Pine** |
| Place the order | Alpaca paper (TradingView has no order API) |

**Re-export after every retrain**, or the chart silently keeps scoring with a
stale model — the weights are frozen constants, not a live link.
